## ③ 指示の解釈と省略の解決

| 構成要素 | 実装 | ギャップ |
| --- | --- | --- |
| 自然文の指示を、トーン・保留・用件に分ける | `parseInstruction`（`chatgpt-app/src/reply.js`） | 語彙は「丁寧」「はっきり」「冷静」「砕け」「保留」などに限る。LLMでは読まない |
| 指示のトーンを候補へ反映する | `applyInstruction` が `tone` を上書きし、`buildCandidates` が使う | 文面がトーンを名指ししたときだけ、フォームの選択より優先する |
| 「さっきの人に」などを、直前のしおりの相手・件名・抜粋へ解決する | `applyInstruction` と `prepareInput`（`chatgpt-app/src/mcp.js`）。履歴は `listShiori` | しおりが無いときは解決しない。相手の名前は推測しない |
| 解決結果を画面に出す | ウィジェットの `referenceLine` | 複数の「さっき」を区別しない。直近の1件だけ |

## ② 感情影響の可視化

| 構成要素 | 実装 | ギャップ |
| --- | --- | --- |
| 候補ごとに、相手が受け取りそうな気持ちの分類・点数・理由を出す | `predictRecipientEmotion`。結果は各候補の `emotion` | 規則による予測。相手に聞いた結果でも、感情認識モデルでもない |
| 候補を並べ、気持ちを見比べて選べる | ウィジェットの `#emotionCompare` と各カードの「相手の気持ち」 | 並びは最大3件。利用者が点数の重みを変える画面は無い |
| 高リスクや「保留にして」でも、候補ごとに気持ちが分かれる | 保留3種（安心・納得・負担）を `buildCandidates` が付ける | 危険度（送ってよいか）とは別の軸。危険度の代わりにはしない |

## ① 候補、危険度、人間の確認

| 構成要素 | 実装 | ギャップ |
| --- | --- | --- |
| 受信文から危険度の点数と理由を出す | `assessMessage`。高リスク語は `backend/src/triage.js` と同じ | 本文・件名・差出人の文字列だけ。メールヘッダの CC/BCC は読まない |
| 複数の返信候補を作る | `buildCandidates` | 定型文。LLMの下書きは呼ばない |
| 高リスクは約束しない保留文だけにする | `buildCandidates` の holding 分岐 |  |
| 人が確認するまでコピー文面を渡さない | `reviewConfirmation`。高リスクは追加の確認が必要 | モデルが `humanConfirmed: true` を付けて呼ぶことは、ツール定義ではアプリ側に限っている |

## ⑲ しおり

| 構成要素 | 実装 | ギャップ |

## ㊚ 最終動作の直前に状態を取り直す

| 構成要素 | 実装 | ギャップ |
| --- | --- | --- |
| 候補を作った時点の文面と危険度を保存する | `storeSnapshot`。キーは `snapshot:<id>`。24時間で消える | KV が無い環境では保存できない。`stateCheck` は `not_stored` |
| コピーの直前に保存を読み直し、文面か危険度が違えば渡さない | `compareSnapshot` と `confirm_candidate` | 不一致の理由は `state_mismatch`。作り直して再確認する |
| 送信や外部サービスへの反映はしない | コピー用の文字列を返すだけ。`sent` は常に false | 送る経路が無いので、再取得の対象はコピーだけ。実メールや LINE の再送前確認は対象外 |

不一致のとき、ウィジェットは「内容が変わったので、候補を作り直して、もう一度確認してください。」と出します。
